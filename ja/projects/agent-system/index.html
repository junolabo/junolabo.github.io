課題

ドリンク製造ロボットは固定された製造手順に従っていました。固定された手順では、メニューにない要望や実行中に起きた問題を処理できず、そのたびに人が介入していました。目標は、有人店舗のように柔軟に対応し、社屋内の配送と清掃まで任せることでした。

  1. 状況は組み合わさり、ルールではその組み合わせを書ききれません。LLMは、あらかじめ決められていない状況を判断できます。LLMが計画を担当する理由です。
  2. LLMのplanは、誤っていてももっともらしく見えます。そのロボットにないskillを使う、順序を誤る、現在の状態ではできないことを指示する、依頼されていない作業を加える、といったことが起こり得ます。
  3. ロボットの成功応答が、そのまま結果とは限りません。ロボットが動作の完了を応答しても、意図した結果が実際には起きていないことがあります。
  4. ロボットがそれぞれ異なります。レール型マニピュレータ、双腕のセミヒューマノイド、配送ロボット、清掃ロボットは、skillと制約がそれぞれ異なります。

構成

仕組み

Orchestrator Agent

運用中（社内） / 実機テスト

自然言語の依頼を作業に分け、MCP toolとして接続したagentとロボットに配分します。「アメリカーノ2杯を会議室へ」という依頼であれば、製造と積み込みはドリンク製造agentに、配送は配送ロボットに任せます。VLMが汚れを検知すると清掃ロボットを向かわせます。セミヒューマノイドagentへの配分は実機テスト段階です。

Task Planning Agent（ドリンク製造ロボット）

運用中（社内） / 実機テスト

カップ・氷の払い出し、ドリンクの抽出、ロボットアームの移動、積み込みのskillをLLMが組み合わせて製造手順を計画します。手順は固定しません。ルールは手順ではなく制約として与えます。アイスドリンクはカップ、氷、ドリンクの順である必要があり、その中で残りはplannerが決めます。

ディスペンサーのチャンネルの種類・状態・在庫、ロボット、カップ、区画の状態をgraphとして持ち、実行中に更新します。同じチャンネルが繰り返し失敗した場合は使用不可とし、別のチャンネルを使います。現在の注文に関する短期メモリと、過去の対応事例に関する長期メモリを持ちます。

状態agentが行うこと
運用中（社内）社内配送注文の製造と配送ロボットへの積み込み。失敗した場合は残りの計画を作り直す
実機テストメニューにない要望（氷水）、カスタムドリンク（ショット追加）、VLMが検知した異常への対応順序の判断。店舗のお客様にはまだ提供していない

Task Planning Agent（セミヒューマノイドロボット）

実機テスト

「塩パンを2個入れて」のような注文を、cameraで商品を探す → 対象を選ぶ → pick-and-place の繰り返しとして計画します。袋に入れる直前ごとに対象が残りの注文にあるかを確認し、注文と異なる商品を入れません。袋の中身が注文と正確に一致して初めて、作業の完了とします。

失敗は4段階で復旧します。ルールによる補正、LLMによる修正、再計画、人への依頼の順です。把持に失敗すれば再試行し、落とせば再検索し、在庫がなければ残りの注文を再計画するか人を呼びます。ロボットとの接続はexecuteとobserveの2つの契約に絞り、mock、simulator、実機を差し替えられます。

Context Manager

運用中（社内）

ロボットの位置、持っている物体、機器の在庫などの現在の状態をworld stateとscene graphとして保持し、依頼に必要な部分だけをLLMの入力として構成します。状態は上書きしません。観測を時刻と出所とともに蓄積し、そこから現在の状態を計算するため、古い観測を現在と取り違えません。完了は、ロボットの成功応答ではなくobservationで確認します。

Plan Validator

運用中（社内）

LLMが作ったplanをロボットに送る前に、現在のworld state上で1ステップずつ事前に実行します。plannerは2段階で動きます。まず自然言語で計画を書き、その意味を保ったまま構造化された形に変換します。validatorは構造化されたplanを検査します。

検査すること止められるplanの例
各ステップがそのロボットのskillかそのロボットにないskillを使うステップ
順序が正しいか製造が終わる前の配送
位置・積載容量・機器の状態から実行可能か積載上限を超えるドリンク数
依頼された作業かhallucinationによって加わった、依頼されていない作業

結果は、valid、conditional、violation、undecidableの4つのいずれかです。通過しなかったplanは、理由を付けてplannerに戻します。検証の後にworld stateが変わった場合は、planをそのまま送らず、もう一度検証します。

Planning evaluation

シミュレーション

依頼ごとに必須条件（例：製造が終わってから配送、積載上限の順守）を定めます。planと実行結果を別々に採点します。評価も実際の運用と同じcode経路で実行し、正解条件はplannerに与えません。生成の段階で止まった事例も分母から外しません。この部分はチームメンバーと共同で開発しました。

ルールの限界

分類状況例
1. 通常運用メニューにあるもの、ないもの、無料で提供できるもの氷水
2. 単独の異常把持の失敗、抽出の失敗、提供中のこぼれ、人の接近、放置されたドリンク把持の失敗 → カップを再度払い出す
3. 複合的な状況カスタムメニュー、事故対応と運用の優先順位、複数の問題の同時発生こぼれた後、再製造が先か清掃が先か。空いている区画の数と待ち注文の有無によって変わる

状況が組み合わさると、場合をルールとして書ききれなくなります。3がその地点です。

設計上の決定

決定理由防ぐ問題
LLMは計画のみ。検証と実行はcodeが行うLLMは決められていない状況を判断できるが、誤ることもある誤ったplanがロボットに届くこと
planを送る前に、world state上で事前に実行する実行可能かどうかは、planの文面ではなく現在の状態で決まる文面は正しいが実行できないplan
完了をobservationで確認する成功応答は動作が終わったという意味であり、結果が正しいという意味ではない実際には成功していないステップの上で、planを続けること
ルールを固定の手順ではなく制約として与える固定の手順では、メニュー外の要望を扱えない新しい要望のたびに手順を書き直すこと
agentの有無にかかわらず、すべてのロボットをtoolとして接続するロボットごとにskillと制約が異なるロボットごとに別々の接続方式

製造中に1つのステップが失敗

運用中（社内）

状況カップを払い出したが、gripper cameraではカップが把持されていない

  1. カップの払い出し
  2. 把持確認の失敗
  3. 再計画カップの払い出しから
  4. カップを再度払い出し
  5. 製造を続行

失敗または戻る経路

失敗skill自体は実行されたが、その後のobservationでカップが把持されていないと確認される
再計画Task Plannerが、カップの払い出しから残りの計画を作り直す
繰り返しの失敗同じチャンネルが失敗し続ける場合は使用不可とし、別のチャンネルを使う

メニューにない要望

実機テスト

状況ある依頼は氷水、別の依頼はショットを追加したドリンク

  1. 依頼
  2. 判断提供してよいか
  3. Task Planner (LLM)既存のskillを組み合わせる
  4. Plan Validator
  5. 製造
判断氷水は販売メニューではないが提供できる。販売メニューのドリンクは無料では提供しない
計画固定の製造手順ではこれらの要望を扱えない。plannerが制約の中で既存のskillを組み合わせる
検証と実行ほかのplanと同じ検証を通過してから実行
