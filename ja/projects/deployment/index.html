Project 1-3

Deployment & Model Update

40店舗以上のruntimeとモデルを遠隔で更新します。新しいバージョンと新しいモデルは、検査を通過した後にのみ店舗に配布されます。

課題

この作業の前は、開発者が手作業でソフトウェアをデプロイし、モデルを更新していました。店舗が増えるにつれ、その方式では対応できなくなりました。

  1. 店舗は互いに同じではありません。棚のサイズ、ロボット構成、cameraの種類が店舗ごとに異なります。
  2. ある店舗で良くなったモデルが、別の店舗で悪くなることがあります。ひとつの店舗のデータで学習すると、モデルがその店舗に偏ります。
  3. 誤ったデプロイは店舗を止め、現場には人がいません。問題は、運用中のサービスを切り替えた後ではなく、切り替える前に見つける必要があります。

構成

3つの部分が店舗の全過程を担当します。commissioningは新規店舗を運用状態にし、OTAはruntimeを届け、MLOps pipelineはモデルを最新に保ちます。

仕組み

MLOps pipeline

運用中

stereo、detection、VLMの3つのモデルに適用しています。人がすべてのデータを見ることはありません。モデルの判断が変わった区間や信頼度が低い区間をpipelineが選び、自動でラベリングし、人がラベルを確認して修正します。

OTA

運用中

デプロイの単位はruntime全体です。中央サーバーがTailscaleで店舗の機器に接続し、Ansibleでデプロイします。新しいバージョンは、運用中のサービスをすぐには置き換えません。まずdry-runとして動かし、以前のバージョンと動作を比較します。

Commissioning

運用中

店舗ごとに異なる棚のサイズ、ロボット構成、cameraの種類を、codeの分岐ではなく設定で扱います。すべての店舗で同じruntimeが動きます。calibrationの結果をバージョン管理しているため、店舗を以前のcalibrationに戻せます。

設計上の決定

各行は、ひとつのリスクと、それを止める段階です。

リスク止める段階部分
モデルがある店舗で良くなり、全体では悪くなる対象店舗と全店舗を別々に評価。両方の通過が必要MLOps pipeline
新しいモデルが使用中のモデルより良くない使用中のモデルより良いことも必要MLOps pipeline
自動ラベルが誤っている学習の前に人が確認して修正するMLOps pipeline
新しいバージョンにエラーがある、他の機器との通信が壊れる、判断結果が変わる切り替えの前に、dry-runを以前のバージョンと比較するOTA
デプロイ後に店舗の動作がおかしくなる店舗のログをリアルタイムで収集し、異常時に通知するOTA
新規店舗の棚、ロボット、cameraが異なる違いを設定として書く。codeは分岐しないCommissioning
calibrationが誤っていたと分かるcalibrationの結果をバージョン管理。以前のバージョンに戻すCommissioning
