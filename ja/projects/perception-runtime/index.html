Project 1-1

Perception Runtime

スタッフのいない店舗で、2台のcameraがピックアップ棚とカップ1杯ごとの状態を判断します。どの区画（slot）が空いているか、ドリンクが正しく出たか、お客様が受け取ったかを判断します。

課題

ロボットは完成したドリンクをピックアップ棚の区画に置き、お客様はそこから受け取ります。棚を見ている人がいないため、棚に関するすべての判断は、棚の上の天井cameraとロボットの手元のgripper cameraから得ます。

  1. カップが消えても、お客様が受け取ったとは限りません。ロボットも、受け取られなかったドリンクを廃棄するときにカップを取り除きます。映像だけでは2つの場合は同じに見えます。
  2. depthがないことと、区画が空いていることは違います。depthが途切れたり古くなったりすると、区画上の高さは分かりません。分からないことを空きと読むと、すでにあるカップの上に新しいドリンクを置いてしまいます。
  3. 光は店舗や時間帯で変わり、cameraはガラスを見ています。自然光と複数の室内照明は店舗ごとに異なり、cameraが主に見る領域はガラスのディスプレイ面です。既存のdepthでは、そこで信頼できる値が得られませんでした。
  4. 1本のロボットアームがドリンクを作り、片付けも行います。廃棄の作業が製造と重なってはいけません。片付けるカップは、ほかのお客様のカップの隣に置かれています。

構成

仕組み

Occupancy detection

運用中

占有はdepthで判断します。学習したstereoモデルのdepthとRealSense自体のdepthを棚面基準の座標に変換し、各区画に置かれた物体の高さを測ります。depth自体にも、正常、古い、不良の3つの状態を持たせています。正常でない間は区画を空きとして出力せず、その区画に新しいドリンクを置きません。

以前の方式：2.5D特徴を使う分類モデルが区画の状態を判断していました。物理的な高さで判断する方式の方がよく汎化したため、現在の方式に置き換えました。

Cup lifecycle tracking

運用中

カップ1杯を製造からお客様の受け取りまで追跡します。製造の後、gripper cameraでカップを正しく把持できたかとドリンク量を確認します。棚の上では天井cameraがカップを追います。detectionとtrackingはC++とTensorRTで実装しました。

同じ観測でも、その瞬間にロボットが何をしているかによって意味が変わります。

Camera観測ロボットの作業状態判断
天井置いたカップが棚にないそのカップの回収作業なしお客様の受け取り
天井置いたカップが棚にないロボットがそのカップを回収中ロボットによる回収。受け取りとして扱わない
Gripperカップを正しく把持したか、ドリンク量製造の直後棚に置く前の完成ドリンクの確認
Gripper手元の前にあるカップ廃棄するカップを把持する直前天井cameraが選んだカップかどうか

区画の割り当てとカップの記録はSQLiteに一緒に書き込み、commitの後にのみ状態を発行します。そのため、システムのほかの部分が保存されていない状態をもとに動くことはありません。再起動後もSQLiteから状態を復元します。

Disposal flow

運用中

お客様が受け取らなかったドリンクをロボットが把持して廃棄します。以前は管理者が店舗に出向いて行っていた作業です。

Stereo depth

運用中

上記の判断はdepthに依存しますが、depthが弱点でした。光の条件が店舗や時間帯で変わり、関心領域がガラス面だったためです。そこで、この棚に合わせたstereo depthモデルを学習しました。

1件を最後まで追う

カップ1杯が、製造から記録が終わるまでにたどる流れです。

出来事観測判断結果
ドリンクの製造Gripper camera：把持、ドリンク量正しく把持し、量も適切棚に置いてよい
区画が必要天井camera：区画ごとの高さ、depthの状態は正常この区画は空いているロボットがカップを置く。区画の割り当てとカップの記録をcommitしてから発行

runtimeの再起動SQLite—区画の割り当てとカップの記録を復元
