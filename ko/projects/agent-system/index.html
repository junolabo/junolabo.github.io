Project 2

Heterogeneous Multi-Robot Agent System

LLM이 계획하고 code가 검증합니다. 음료 제조 로봇과 세미 휴머노이드 로봇에는 Task Planning Agent를 두고, 배송 로봇과 청소 로봇은 tool로 호출합니다. Orchestrator Agent가 로봇 4종을 묶습니다.

문제

음료 제조 로봇은 고정된 제조 순서를 따랐습니다. 고정된 순서로는 메뉴에 없는 요청이나 실행 중에 생긴 문제를 처리할 수 없어, 그때마다 사람이 개입했습니다. 목표는 유인 매장처럼 유연하게 응대하고, 회사 건물 안의 배송과 청소까지 맡기는 것이었습니다.

  1. 상황은 조합되고, 규칙으로는 그 조합을 다 쓸 수 없습니다.LLM은 미리 정해지지 않은 상황을 판단할 수 있습니다. LLM이 계획을 맡는 이유입니다.
  2. LLM의 plan은 틀려도 그럴듯해 보입니다.그 로봇에 없는 skill을 쓰거나, 순서를 틀리거나, 지금 상태로는 할 수 없는 일을 시키거나, 요청하지 않은 작업을 넣을 수 있습니다.
  3. 로봇의 성공 응답이 곧 결과는 아닙니다.로봇이 동작을 끝냈다고 응답해도, 의도한 결과가 실제로 일어나지 않았을 수 있습니다.
  4. 로봇들이 서로 다릅니다.레일형 매니퓰레이터, 양팔 세미 휴머노이드, 배송 로봇, 청소 로봇은 skill과 제약이 서로 다릅니다.

구조

동작

Orchestrator Agent

운영 (사내) / 실로봇 테스트

자연어 요청을 작업으로 나눠, MCP tool로 연결한 agent와 로봇에 배분합니다. “아메리카노 2잔을 회의실로” 요청이면 제조와 적재는 음료 제조 agent에, 배송은 배송 로봇에 맡깁니다. VLM이 오염을 감지하면 청소 로봇을 보냅니다. 세미 휴머노이드 agent로의 배분은 실로봇 테스트 단계입니다.

Task Planning Agent (음료 제조 로봇)

운영 (사내) / 실로봇 테스트

컵·얼음·음료 추출, 로봇팔 이동, 적재 skill을 LLM이 조합해 제조 순서를 계획합니다. 순서를 고정하지 않습니다. 규칙은 순서가 아니라 제약으로 줍니다. ICE 음료는 컵, 얼음, 음료의 순서여야 하고, 그 안에서 나머지는 planner가 정합니다.

디스펜서 채널의 종류·상태·재고, 로봇, 컵, 칸의 상태를 graph로 두고 실행 중에 갱신합니다. 같은 채널이 반복해서 실패하면 사용 불가로 표시하고 다른 채널을 씁니다. 현재 주문에 대한 단기 메모리와 과거 대응 사례에 대한 장기 메모리를 둡니다.

상태agent가 하는 일
운영 (사내)사내 배송 주문의 제조와 배송 로봇 적재. 실패하면 남은 계획을 다시 만듦
실로봇 테스트메뉴에 없는 요청(얼음물), 커스텀 음료(샷 추가), VLM이 감지한 이상 상황의 대응 순서 판단. 매장 고객에게는 아직 제공 전

Task Planning Agent (세미 휴머노이드 로봇)

실로봇 테스트

“소금빵 2개 담아줘” 같은 주문을 camera로 상품 찾기 → 대상 선택 → pick-and-place의 반복으로 계획합니다. 담기 직전마다 대상이 남은 주문에 있는지 확인해, 주문과 다른 상품을 담지 않습니다. 봉투에 담긴 내용이 주문과 정확히 일치해야 작업이 끝난 것으로 봅니다.

실패는 네 단계로 복구합니다. 규칙에 의한 보정, LLM의 수정, 재계획, 사람에게 요청의 순서입니다. 잡기에 실패하면 재시도하고, 놓치면 다시 검색하고, 재고가 없으면 남은 주문을 재계획하거나 사람을 호출합니다. 로봇과의 연결은 execute와 observe 두 가지 계약으로 줄여, mock, simulator, 실로봇을 바꿔 끼울 수 있습니다.

Context Manager

운영 (사내)

로봇 위치, 들고 있는 물체, 장비 재고 같은 현재 상태를 world state와 scene graph로 유지하고, 요청에 필요한 부분만 LLM 입력으로 구성합니다. 상태를 덮어쓰지 않습니다. 관측을 시간, 출처와 함께 쌓고 거기서 현재 상태를 계산하므로, 오래된 관측을 현재로 착각하지 않습니다. 완료는 로봇의 성공 응답이 아니라 observation으로 확인합니다.

Plan Validator

운영 (사내)

LLM이 만든 plan을 로봇에 보내기 전에 현재 world state 위에서 한 단계씩 미리 실행합니다. planner는 두 단계로 동작합니다. 먼저 자연어로 계획을 쓰고, 그 뜻을 유지한 채 구조화된 형태로 바꿉니다. validator는 구조화된 plan을 검사합니다.

검사하는 것막히는 plan의 예
각 단계가 그 로봇의 skill인가그 로봇에 없는 skill을 쓰는 단계
순서가 맞는가제조가 끝나기 전의 배송
위치·적재 용량·장비 상태로 수행 가능한가적재 한도를 넘는 음료 수
요청한 작업인가hallucination으로 들어간, 요청하지 않은 작업

결과는 valid, conditional, violation, undecidable의 네 가지 중 하나입니다. 통과하지 못한 plan은 이유를 붙여 planner로 되돌립니다. 검증한 뒤에 world state가 바뀌면 plan을 그대로 보내지 않고 다시 검증합니다.

Planning evaluation

시뮬레이션

요청마다 필수 조건(예: 제조가 끝난 뒤 배송, 적재 한도 준수)을 정합니다. plan과 실행 결과를 따로 채점합니다. 평가도 실제 운영과 같은 code 경로로 실행하고, 정답 조건은 planner에 주지 않습니다. 생성 단계에서 막힌 사례도 분모에서 빼지 않습니다. 이 부분은 팀원과 공동으로 개발했습니다.

규칙이 끝나는 지점

분류상황예
1. 일반 운영있는 메뉴, 없는 메뉴, 무료로 줄 수 있는 것얼음물
2. 이상 상황 단독컵 그립 실패, 음료 추출 실패, 서빙 중 쏟아짐, 사람 접근, 방치 음료그립 실패 → 컵을 다시 추출
3. 복합 상황커스텀 메뉴, 사고 처리와 운영 사이의 우선순위, 여러 문제의 동시 발생쏟아진 뒤 재제조가 먼저인가 청소가 먼저인가. 빈 칸의 수와 대기 주문의 유무에 따라 달라짐

상황이 조합되면 경우를 규칙으로 다 쓸 수 없습니다. 3번이 그 지점입니다.

설계 결정

결정이유막는 문제
LLM은 계획만 함. 검증과 실행은 code가 함LLM은 정해지지 않은 상황을 판단할 수 있고, 틀릴 수도 있음틀린 plan이 로봇에 도달하는 것
plan을 보내기 전에 world state 위에서 미리 실행수행 가능 여부는 plan의 글이 아니라 현재 상태에 달려 있음글로는 맞지만 수행할 수 없는 plan
완료를 observation으로 확인성공 응답은 동작이 끝났다는 뜻이지, 결과가 맞다는 뜻이 아님실제로는 성공하지 않은 단계 위에서 plan을 이어 가는 것
규칙을 고정된 순서가 아니라 제약으로 줌고정된 순서로는 메뉴 밖의 요청을 다룰 수 없음새 요청마다 순서를 다시 쓰는 것
agent가 있든 없든 모든 로봇을 tool로 연결로봇마다 skill과 제약이 다름로봇마다 다른 연결 방식

메뉴에 없는 요청

실로봇 테스트

상황한 요청은 얼음물이고, 다른 요청은 샷을 추가한 음료임

  1. 요청
  2. 판단제공해도 되는가
  3. Task Planner (LLM)기존 skill을 조합
  4. Plan Validator
  5. 제조
판단얼음물은 판매 메뉴가 아니지만 제공할 수 있음. 판매 메뉴의 음료는 무료로 제공하지 않음
계획고정된 제조 순서로는 이 요청을 다룰 수 없음. planner가 제약 안에서 기존 skill을 조합
