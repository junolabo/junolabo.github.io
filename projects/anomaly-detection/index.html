The problem

Checking whether something went wrong in a store used to need a person: a manager who went to the store, or an operator who watched remotely. To run without them, the system has to notice the situation and also decide what to do about it.

  1. Anomalies have no fixed shape.A fallen cup, contamination, an equipment failure, and many others. Writing a separate rule or detector for every kind does not keep up with the kinds that appear.
  2. The image alone is not enough.An image does not show what the robot and the equipment are doing at that moment. The state has to be read together with the image.
  3. A wrong classification must not turn into a robot action.A model can be wrong, and its output can be malformed. Something has to stand between the model and the robot.
  4. The store was already in operation.The new function had to be added without changing the interfaces of the running system.

Structure

How it works

VLM anomaly detection

In operation at company-run stores

Camera images and robot and equipment state are bundled every 2 seconds and given to the VLM. The VLM is a small model fine-tuned with QLoRA on store situations, and it classifies 12+ kinds of situations such as a fallen cup, contamination, and equipment failure.

The model's output is forced into a fixed schema, so code can parse it. Before the result is used, rule-based checks written in code look at it: whether the inputs were fresh, whether the nodes that supplied them were healthy, and whether the result is consistent with rules such as a hand entering the area or a spill.

Earlier version: an image anomaly detector found spills and heavy contamination and blocked serving on that slot. The VLM replaced it because a VLM fits situations that have no fixed shape better.

Response by situation

The principle: what the robot can fix, the robot fixes. What needs a person raises an alert.

SituationResponseWho acts
A cup fell over. Nothing spilled.The cup is picked up and disposed of.Robot
A cup fell over and the drink spilled.The manager is called.Person
Contamination inside the buildingThe Orchestrator Agent dispatches the cleaning robot.Cleaning robot
A critical equipment failureAn alert is sent.Person

Improving the model with reviewed cases

Cases where a person's review disagreed with the model go into the next training data. The VLM is one of the three models updated by the MLOps pipeline.

Design choices

ChoiceReasonWhat it prevents
The image is bundled with robot and equipment state.An image does not show what the robot is doing.Judging a situation from the image alone.
The output must follow a fixed schema.Free text cannot be used to choose a response.Output that cannot be parsed.
Rule-based checks stand between the VLM and the action.The model can be wrong.A wrong result becoming a robot action.
It runs as a read-only sidecar next to the running system.The store was already in operation.Changing the ROS 2 interfaces of the running system.
The VLM only recognizes. It does not choose or control the robot's motion.The response to each kind of situation is defined outside the model.The model's output directly moving the robot.

One case, start to end

A cup falls over in the store

In operation at company-run stores
ObservationCamera images and robot and equipment state are bundled. This happens every 2 seconds.
ClassificationThe VLM returns the kind of situation in the fixed schema.
CheckRule-based checks confirm that the inputs were fresh and that the result is consistent with the rules.
ResponseNothing spilled: the robot picks up the cup and disposes of it. The drink spilled: the manager is called.

Today a predefined flow carries out the response. Letting the Task Planning Agent decide the order of responses (dispose, remake, clean) is in real-robot testing.
