The problem

Before this work, a developer deployed software and updated models by hand. That stopped being workable as the number of stores grew.

  1. Stores are not the same.Shelf size, robot configuration, and camera type differ from store to store.
  2. A model that improves at one store can get worse at another.Training on data from one store pulls the model toward that store.
  3. A bad deployment stops a store, and nobody is there.A problem has to be found before the running service is replaced, not after.

Structure

Three parts cover the life of a store: commissioning brings a new store into operation, OTA delivers the runtime, and the MLOps pipeline keeps the models current.

How it works

MLOps pipeline

In operation

The pipeline is applied to three models: stereo, detection, and VLM. People do not look at all the data. The pipeline selects the segments where the model's decision changed or where its confidence was low, labels them automatically, and a person reviews and corrects the labels.

OTA

In operation

The unit of deployment is the whole runtime. A central server reaches the store devices over Tailscale and deploys with Ansible. The new version does not replace the running service at once. It first runs as a dry-run, and its behavior is compared with the previous version.

Commissioning

In operation

Differences between stores, such as shelf size, robot configuration, and camera type, are handled by configuration and not by code branches. The same runtime runs in every store. Calibration results are kept as versions, so a store can be returned to an earlier calibration.

Design choices

Each row is a risk and the step that stops it.

RiskWhat stops itPart
A model improves at one store and gets worse overall.It is evaluated separately on the target store and on all stores. Both must pass.MLOps pipeline
A new model is no better than the one in use.It must also be better than the current model.MLOps pipeline
Automatic labels are wrong.A person reviews and corrects them before training.MLOps pipeline
A new version has an error, breaks communication with other devices, or changes decisions.The dry-run is compared with the previous version before the swap.OTA
A store misbehaves after a deployment.Store logs are collected in real time, and an anomaly raises an alert.OTA
A new store has a different shelf, robot, or camera.The difference is written as configuration. The code is not branched.Commissioning
A calibration turns out to be wrong.Calibration results are versioned. The store returns to the earlier version.Commissioning
